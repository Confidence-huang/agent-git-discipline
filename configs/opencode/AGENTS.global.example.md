# opencode 全局规则示例（Git 纪律部分）

> **用途**：可直接放到 `~/.config/opencode/AGENTS.md`（Windows 为
> `%USERPROFILE%\.config\opencode\AGENTS.md`）的示例，只含 Git 纪律相关章节。
>
> **已脱敏**。建议**追加**到你已有的全局规则，而不是整体覆盖。
>
> ⚠️ 注意：opencode 的全局规则若把 `commit` 列入"需确认"清单，
> 会与项目托管块的"立即 commit"冲突——**必须二者取一**。本示例选择默认授权。

## 1. 配置/既有文件修改原则（硬性规则）

修改任何"既有配置、订阅自带规则、用户自己写好的文件"前，必须遵守：

1. **先备份再改**：有 git 跟踪的文件靠 git 回退，改动前先用 `git status`/`git diff`
   确认改动可追踪，较大改动先本地 commit 一个基线；无 git 跟踪的用户级文件
   用复制方式备份到备份根，确认备份成功后再动原文件，不生成就地 `*.bak.*`。
2. **优先最小改动**：能删一条就只删一条、能追加就追加，不整体重写既有文件。
3. **删除既有内容前先说明影响**：要删什么、删了会不会影响其他功能，得到用户确认后再执行。
4. **区分"订阅源文件"与"增强/合并文件"**：订阅自带的规则文件原则上不动。

## 7. 执行纪律

### 7.1 风险操作拦截链

涉及删除、迁移、覆盖、全局规则/配置修改、PATH、注册表、junction、未知脚本、安装、
`git branch`/`reset`/`tag`/`push`/PR 时，固定执行：

```
只读诊断 → 输出计划或 diff → 等待用户明确确认 → 逐项备份 → 串行执行 → 验证 → 回报
```

未明确授权停在计划/diff；授权范围不清不扩大。

> **本地 `git commit` 不在本拦截链内** —— 它已默认授权，见 §9。

### 7.2 并行/串行边界

独立只读（文件读取、搜索、状态检查）可并行；
下载→解压→验证、同一文件编辑、依赖前一步、删除/移动/安装/**提交**必须串行。

## 9. Git 纪律

本节与项目托管块 v4、以及 Codex 侧的"代码修改的 Git 闭环"**同源**，避免多侧漂移。

### 9.1 授权边界

| 动作 | 授权状态 |
|---|---|
| `git status` / `diff` / `log` / `show` / `rev-list` | ✅ 默认授权 |
| `git add <本轮明确文件>` | ✅ 默认授权 |
| **本地 `git commit`（单个原子改动）** | ✅ **默认授权，不必逐次确认** |
| 新建/切换分支、`rebase`、`reset`、改写历史、`tag` | ⚠️ 需单独授权 |
| `push`、PR、任何远端操作 | ⚠️ 需单独授权 |
| 删除文件、`git clean`、批量清理 | ⚠️ 需单独授权 |
| `git push --force` | ❌ 禁止；确需时只用 `--force-with-lease` 且限自己分支 |
| 改写已推送历史 | ❌ 禁止，除非用户明确点名要求 |

### 9.2 提交纪律

- 改前核对 Git 根（`git rev-parse --show-toplevel`）、branch、HEAD、index 与目标文件归属；
  不得在不知道仓库边界时直接写代码。
- 首段写入前建本次原子基线；每个通过验证的原子改动只暂存本轮文件 →
  复核 `git diff --staged` → 立即 `commit`。
- 禁 `git add .` / `git add -A`；混杂时用 `git add -p` 逐块挑选；
  **不允许积攒多轮改动一次混合提交**。
- **原子性检验**：只做一件事／代码库仍可工作／message 标题不需要"and"／
  能独立 revert／无需外部上下文即可理解。描述时必须说"和"，就是两个 commit。
- 起点为脏时：**用户的**改动先报告、不擅自提交或丢弃；**上一轮 agent 的**改动
  先提交或 `stash` 存档；**不回退与本轮无关的改动**。
- 秘密一旦提交极难清除（需重写历史），防线必须前移到"根本不提交"；`.gitignore` 本身应入库。

### 9.3 编号与回报

- commit 后运行 `git rev-list --first-parent --count HEAD`，
  记录"第 N 次 git"/完整 commit SHA/文件范围/验证结果。
- 最终回复**最后一条普通文本**写 `已git：<仓库> 第 N 次 git（commit <短SHA>）`；
  无 commit 写 `本轮未git：原因`；编号是给人用的回退别名，精确回退仍以 SHA 为准。
- 涉及**多个仓库**时**逐个仓库各写一行**；单仓库也**不省略** `<仓库>`，否则事后分不清是哪一份回报。
- 提交失败必须报 `GIT_BLOCKED`，**不得把未提交代码声称为完成**，不得伪造编号。

### 9.4 回退

- 优先 `git revert`（保留历史，可安全推送）；
  `git reset --hard` / `git clean` 属危险操作需授权；`git reflog` 是最后保险。
- 回退前先预览（`git clean -nd`）或存档（`git stash -u`）。

### 9.5 与 §7.1 的关系

**本地 commit 走本节（默认授权）**；其余 git 写操作（branch/reset/tag/push/PR/删除）
仍走 §7.1 拦截链。

## 10. 规则自进化机制

### 10.1 进化闭环（无需用户提醒，主动执行）

1. **触发**：用户纠正/返工、踩坑、工具链变化、新工作流验证成功、用户表达新偏好。
2. **记录**：完整上下文（现象/诊断/证据/结论/路径）先落到当前项目 `PROJECT_LOG.md`。
3. **提炼**：把可复用结论**增量**沉淀进本文件或规则档案；只留结论，不留过程。
4. **核对**：**全文搜索**关键触发词是否覆盖到所有入口；漏了就在对应入口补。
5. **上报**：回复末尾报告 `规则已更新：<改了哪节/哪条>`。

### 10.2 硬门槛

- 规则文件本身的修改走 §1 备份 + 最小改动；
  复盘日志、记忆摘要、单个项目文件**不能替代**规则入口。
- 规则更新要可回退：保留备份；旧版内容留在 git 历史。
- 不因借鉴而整体重写既有文件；只 append/局部改。

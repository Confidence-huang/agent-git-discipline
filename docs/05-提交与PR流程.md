# 05 · 提交与 PR 流程

本文回答 `SKILL.md` **故意没有展开**的那个问题：

> 改动做完之后，什么时候可以直接提交到 `main`，什么时候必须开分支走 PR，
> 以及 `push` / PR 这一步到底由谁授权。

`SKILL.md` §1 只写了一行「`push`、PR、任何远端操作 → ⚠️ 必须单独授权」。
那行是**边界**，本文是**流程**。

> ⚠️ **诚实声明**：本项目的 PR 相关条款**不是**从多人协作实战里验证出来的。
> 本项目自身是单人仓库、长期直接提交 `main`，PR 链路只有 CI 侧门禁被真实验证过。
> 各条目的验证状态见 §七，请按那里的标注取用。

---

## 一、先明确前提：本项目**不强制** PR

这与 [01-参考来源.md](01-参考来源.md) 中「与 langfuse 的差异」表一致——我们明确**不采纳**
"强制 feature branch + PR + 评审机器人"：

| 场景 | 分支模型 | 理由 |
|---|---|---|
| 单人 / 本地仓库（本项目的常态） | **直接 commit 到 `main`** | 开分支 + PR + 自己审自己是纯开销 |
| 共享分支 / 多人协作 | **必须** feature branch + PR | 直推 `main` 会覆盖或冲掉他人工作 |
| 需要机器门禁拦住某类改动 | **必须** PR | 门禁挂在 `pull_request` 事件上时，只有 PR 能触发 |

判据只有一条，问自己：

```
这个改动会不会影响我以外的人，或者需要一道机器门禁？
  会   → 走 PR
  不会 → 直接提交
```

**不要为了"看起来规范"而开 PR。** 单人仓库里每个改动都开 PR，会让 `main` 的历史变成
一串无意义的 merge，反而破坏 `git revert` 的可读性。

## 二、授权边界（本文档的硬约束）

下表是 `SKILL.md` §1 的展开版。⭐ 标记的两行是**本文档新增的细分**。

| 动作 | 授权状态 |
|---|---|
| `git status` / `diff` / `log` / `show` / `remote -v` | ✅ 默认授权 |
| `git add <本轮明确文件>`、本地原子 commit | ✅ 默认授权 |
| ⭐ 在**已存在的**特性分支上继续 commit | ✅ 默认授权（与普通提交同待遇） |
| `git remote add` / 改远端 URL | ⚠️ **必须单独授权** |
| `git switch -c <新分支>` / `git branch` / `git tag` | ⚠️ **必须单独授权** |
| `git push` / `git push -u` | ⚠️ **必须单独授权** |
| ⭐ 开 PR / 改 PR 标题或描述 / 评论 / 请求评审 | ⚠️ **必须单独授权** |
| ⭐ 合并 PR / 关闭 PR / 删远端分支 | ⚠️ **必须单独授权** |
| `git push --force` | ❌ **禁止**（尤其共享分支） |
| 改写已推送历史（`rebase` / `amend` + force） | ❌ **禁止**，除非用户明确点名要求 |

### 授权不自动延展

用户说「上传」「推送」时，视为对**那一次 push** 的授权，**不自动延展**到：

- 合并 PR
- 删除远端分支
- 再推一次（哪怕只是"顺手补个 typo"）
- 推**另一个**仓库

跨仓库尤其容易出事：本项目同时维护公开仓库与另一份本地技能仓库，
一次授权**只覆盖一个仓库**，另一个要重新确认。

### Agent 的固定动作

`push` 之前必须先把这两样给用户看：

1. `git diff --staged`（或 `git show --stat`）
2. 本轮的「第 N 次 git」编号与短 SHA

渲染不出 diff 时，用文字描述改了什么，**不得**直接推。

## 三、标准流程

### 步骤 0：核对边界（不可跳过）

```bash
git rev-parse --show-toplevel                            # 真实 Git 根
git status -sb                                           # 分支 + 是否脏
git remote -v                                            # 有没有远端、指向哪
git log --oneline -5                                     # 最近历史
git rev-list --left-right --count origin/main...HEAD      # 领先/落后几个提交
```

最后一条特别重要：它一行同时给出「本地领先几个」和「远端领先几个」。
**落后时先 `fetch` 再决定**，不要在落后状态下推。

### 步骤 1：建分支（需授权）

```bash
git switch -c feat/<简短描述>
```

- 前缀与 commit 类型对齐：`feat/` `fix/` `docs/` `ci/` `chore/`。
- **一个分支只做一个关注点**；混了就先拆，不要靠合并 PR 掩盖。
- 分支名用连字符、全小写、无空格（跨平台与 shell 都安全）。

### 步骤 2：原子提交

沿用 `SKILL.md` §3：只 `git add` 本轮明确文件 → `git diff --staged` 复核 → 立即 commit。

**禁止** `git add .` / `git add -A`——PR 里混进无关文件的成本比本地更高，
评审者会逐行看，而你没法解释为什么 `node_modules` 出现在 diff 里。

### 步骤 3：推送（需授权）

```bash
git push -u origin feat/<简短描述>
```

`-u` 建立跟踪关系，后续 `git status -sb` 才能显示领先/落后。

### 步骤 4：开 PR（需授权）

标题见 §四，描述见 §五。仓库若有 PR 模板，**服从模板**，不要自创结构。

### 步骤 5：等门禁与评审

CI 必须在 PR 上跑起来（见 §六）。**红灯不合并**，也不要"先合并再修"。

### 步骤 6：合并（需授权）

- 默认 **squash** 或 **rebase-and-merge**，让 `main` 保持线性、单提交可 `revert`。
- 合并、关闭、删远端分支**都要单独授权**。
- **合并后用 `git revert`，不要用 `reset`**——`main` 是共享历史，`reset` 会打乱别人的本地副本。

#### 6.1 并行 PR 与 `strict`：第二个必须 rebuild（2026-10-06 实测）

分支保护若开了 **`required_status_checks.strict`**（合并前必须与 base 同步），
**同一时间开着的多个 PR 不能连着直接合**。实测报错原文：

```
X Pull request <owner>/<repo>#33 is not mergeable: the head branch is not up to date with the base branch.
To have the pull request merged after all the requirements have been met, add the `--auto` flag.
To use administrator privileges to immediately merge the pull request, add the `--admin` flag.
```

**这是保护规则在正常工作，不是故障。** 标准动作三步：

```bash
gh pr merge <A> --rebase --delete-branch=false   # 先合第一个
gh pr update-branch <B> --rebase                 # 把第二个 rebase 到新 base（会重写该分支的提交）
# 等 <B> 的必需检查重新跑绿（合并 base 变化会重新触发 CI）
gh pr merge <B> --rebase --delete-branch=false
```

⚠️ `gh pr update-branch --rebase` **会重写分支上的提交**（SHA 变），本地同名分支随之分叉——收尾见 6.2。
⚠️ 不要用 `--admin` 绕过：那等于放弃门禁，只在明确需要并获授权时使用。

#### 6.2 合并后的收尾：先试 `--ff-only`，不可快进才 `reset`

**rebase 合并会在 `main` 上生成等价但不同 SHA 的提交**，于是本地 `main` 与 `origin/main` 分叉。
按这个顺序处理：

```bash
git fetch origin --prune
git switch main
git merge --ff-only origin/main     # 首选：线性快进、无重写、不可能丢内容
```

`--ff-only` 失败（说明本地 `main` 上有未推送的提交）时，才考虑 `git reset --hard origin/main`
——**这属于破坏性操作，需单独授权**；执行前确认那些提交在远端分支上仍然存在
（rebase 合并后源分支通常保留，所以内容不会丢），并记下回退别名（`git reflog`）。

**远端分支默认保留不删**（`--delete-branch=false`），便于回溯 rebase 之前的原始提交。

#### 6.3 收尾核对（机械可查）

```bash
# 每个分支的本地与远端必须一致；不一致就是 6.1 的 update-branch 造成的分叉
for b in main <分支1> <分支2>; do
  printf '%-32s local=%s remote=%s %s\n' "$b" "$(git rev-parse --short $b)" \
    "$(git rev-parse --short origin/$b)" \
    "$([ "$(git rev-parse $b)" = "$(git rev-parse origin/$b)" ] && echo OK || echo DIFF)"
done
```

分叉的本地分支用 `git branch -f <分支> origin/<分支>` 抹平（**该分支未被检出时**才安全；
旧引用仍在 `git reflog` 里，随时可回）。

### 步骤 7：打 tag 与发布（需授权）

- tag 类型**必须与仓库既有 tag 同型**，先判再建：

  ```bash
  git cat-file -t <既有tag>     # 输出 commit = 轻量 tag；输出 tag = 附注 tag
  ```

  轻量用 `git tag <name>`，附注用 `git tag -a <name> -m "..."`；
  不要在一个历来全轻量的仓库里突然塞一个附注 tag（反之亦然）。
- 标题沿用仓库既有格式（本项目是 `v<版本> — <一句话摘要>`），发布正文可直接复用 PR 正文。
- **必须加 `--verify-tag`**：否则 `gh release create` 会自己另建 tag，
  可能出现"本地 tag 与远端 tag 各指一个提交"：

  ```bash
  git tag v<版本>
  git push origin v<版本>
  gh release create v<版本> --verify-tag --title "<标题>" --notes-file <文件>
  ```
- 发布后核对**三者指向同一提交**：

  ```bash
  git rev-parse <tag>
  git ls-remote origin refs/tags/<tag>
  git rev-parse main
  ```

## 四、标题规范

采用 [Conventional Commits](https://www.conventionalcommits.org/)。
注意其**规范正文采用 CC BY 3.0**，引用正文需署名（详见 [README 许可证一节](../README.md#许可证)）。

| 类型 | 用于 |
|---|---|
| `feat` | 新增能力 / 规则 |
| `fix` | 修复错误行为 |
| `docs` | 仅文档 |
| `ci` | 工作流、门禁、构建 |
| `chore` | 杂项、依赖、格式化 |
| `refactor` | 不改行为的重构 |
| `backup` | **本项目的自定义类型**（`bak-local-archives` 用它标记快照刷新） |

格式：`<类型>: <做了什么>`；需要时在正文说**为什么**。

⚠️ **自定义类型允许但要付代价**：Conventional Commits 规则 14 明确允许 `feat` / `fix` 之外的类型，
但**不在此规范内的类型不会被基于该规范的自动化工具识别**（`backup` 不会进 CHANGELOG、
不参与语义化版本推导）。用它的前提是：**该项目内保持一致**，且确实是"规范覆盖不到"的语义。
本项目的历史里出现过的反例值得记住——同一个仓库里 `docs` 与 `doc` 并存、
再用上 `log` / `verify` / `update` / `restore` / `add` / `init` 等类型，
**后果不是"不规范"，而是这些提交对工具彻底隐形**。

**标题里不要出现"和" / "and"**——出现了就说明它是两个 PR。
这正是 `SKILL.md` §3 的「and 检验」在 PR 尺度上的同一结论：

```
feat: 加登录 和 顺手修了日志格式     ❌ 必须拆成两个 PR
feat: 加登录                        ✅
fix: 修正日志格式                    ✅
```

PR 标题与其中的 commit 标题**保持同一套前缀**，否则 squash 后 `main` 的历史会前后不一。

## 五、PR 描述模板

```markdown
## 做了什么
<一句话；与标题同义即可，不要重复粘贴 diff>

## 为什么
<触发问题 / 依据 / 关联 issue>

## 怎么验证
<命令与预期输出；CI 运行链接>

## 回退点
- 本仓库第 N 次 git：<短SHA>（`git rev-list --first-parent --count HEAD`）
- 回退方式：`git revert <短SHA>` / 关闭本 PR

## 未做 / 未验证
<诚实边界；不写在这里的部分会被默认当成已完成>
```

**「回退点」是本节的重点**，也是本项目相对通用 PR 模板的唯一增量：
它把 SHA 包装成人能用的序号，评审者不需要懂 git 也能说"退回到第 20 次"。

**「未做 / 未验证」不是免责声明，是精度声明。** 本项目刻意区分已验证与未验证
（见 [README 验证状态一览](../README.md#验证状态一览)），这个习惯应当延伸到每个 PR。

## 六、门禁：CI 在 PR 上拦什么

以本仓库为例（[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)）：

| 步骤 | 拦什么 |
|---|---|
| `verify_blocks.py` | 改了权威块却忘了同步块副本——**本仓库的核心不变量** |
| `check_repo.py` | 技能 frontmatter 缺失/非 kebab-case、文本文件混入 CRLF、脚本语法错误 |
| `install_skill.sh` 冒烟 | 在隔离 HOME 下验证 link / copy 两种安装模式 |

本地预演（与 CI 等价，PR 之前先自己跑一遍）：

```bash
python3 scripts/verify_blocks.py \
  --block configs/block/GLOBAL-PROJECT-LOG-RULES.v3.md --targets targets.txt
python3 scripts/check_repo.py
```

**为什么门禁要挂在 PR 上**：push 到 `main` 的检查是"事后告警"，
而 `pull_request` 触发器上的检查是"事前拦截"，红灯的 PR 根本合不进去。

### 门禁的三种落点（按可靠性排序）

| 落点 | 何时触发 | 免费私有仓库可用？ |
|---|---|---|
| GitHub 分支保护 + required status checks | 服务端，推送/合并时 | ❌ **不可用**（见 §八） |
| GitHub Actions（`pull_request` 触发器） | PR 上，**合并前** | ✅ 可用 |
| **客户端 Git 钩子**（`core.hooksPath` + `pre-push`） | 本机推送前 | ✅ **唯一可行的强制手段** |

⚠️ **不要把"服务端会拦我"当成假设。** 免费私有仓库拿不到分支保护，API 会直接回：

```
"Upgrade to GitHub Pro or make this repository public to enable this feature."
```

因此客户端钩子是私有仓库唯一能在本机落地的强制点：

```bash
git config core.hooksPath .githooks   # 仓库级；钩子文件入库，但本配置项不入库，克隆后需重设
```

设计原则：钩子尽量**复用仓库已有的校验脚本**（本仓库用 `verify_blocks.py` + `check_repo.py`），
并保留 `git push --no-verify` 作为**有意识的**逃生口——门禁是减速带，不是牢门。

**参考**：[langfuse 的 PR 标题校验 workflow](https://github.com/langfuse/langfuse/blob/main/.github/workflows/validate-pr-title.yml)
——若想让 §四 的标题规范也被机器强制，可照此加一条 `pull_request` 上的标题正则校验。
本项目**未接入**（见 §八）。

## 七、回退：PR 阶段怎么做

| 情况 | 做法 |
|---|---|
| PR 未合并，想改内容 | 直接在分支上**追加 commit** 再 push |
| PR 未合并，描述/标题写错 | 直接改（PR 元数据不是历史，可以放心改） |
| 分支被污染，想推倒重来 | 关掉 PR，从 `main` 重开分支（**需授权**） |
| 已合并到 `main` | `git revert <hash>`，开一个反向 PR |
| 已合并且想连历史一起抹掉 | ❌ 不要在共享分支上 `reset`；用 `revert` |
| 误 `--force` 推坏了分支 | `git reflog` 找回旧 SHA，再用 `--force-with-lease` 推回 |
| 合并后发现块不同步 | CI 会拦住；本地用 `verify_blocks.py` 定位是哪个副本漂移 |

⚠️ **已推送分支上的 `rebase` / `amend` + `--force` 会让评审者看到的历史凭空消失。**
只有在**自己的、未被评审的**特性分支上才允许 `--force-with-lease`，
且必须先 `git fetch` 让 lease 拿到最新远端状态。

**永远不要用 `--force`（无 lease）**：它会在别人刚推了新提交时静默覆盖。

## 八、验证状态与已知边界

如实标注，请按状态取用：

| 项 | 状态 | 说明 |
|---|---|---|
| 单人仓库直接提交 `main` | ✅ **实测验证** | 本项目自身长期如此 |
| CI 在 push / PR 上运行 | ✅ **实测验证** | `.github/workflows/ci.yml` 已实施 |
| 在 PR 上拦住块不一致 | ✅ **实测验证** | 就是 `verify_blocks.py` 的用途 |
| 多人并发 PR（并行分支 + `strict` 必须 rebuild） | ✅ **实测验证**（2026-10-06） | 在 `Confidence-huang/bilibili-douyin-video-learning` 上真实跑过：同时开两个 PR，合完第一个后第二个被 `strict` 拒绝（`the head branch is not up to date with the base branch`）→ `gh pr update-branch --rebase` → 必需检查重跑全绿 → 合并。标准动作见 §三 步骤 6.1 |
| 评审意见往返（他人 review / 请求修改） | ⚠️ **未验证** | 仍是单人仓库，从未真实跑过 |
| 评审机器人 / PR 标题自动校验 | ⚠️ **未接入** | 仅有 §六 给出的参考实现 |
| 分支保护规则（禁止直推 `main`） | ✅ **本仓库已开启**（`enforce_admins: true`） | ⚠️ 免费**私有**仓库不支持（API 返回 `Upgrade to GitHub Pro or make this repository public`）；本项目的**公开**仓库可用，2026-10-02 已开启 required status checks（`一致性检查`）＋ `enforce_admins` |
| 客户端 `pre-push` 门禁 | ✅ **已实施** | `.githooks/pre-push` 复用 CI 的同两步校验；逃生口 `git push --no-verify` |
| 自审 PR（GitHub 官方建议） | ⚠️ **未采用** | 本项目各仓库历年 `PR=0`。官方把「先自审自己的 PR」列为**独立**建议，不需要第二个人 |
| 私有仓库密钥扫描 | ❌ **不可用** | 免费版私有仓库 `security_and_analysis` = `null`（只有公开仓库拿到 secret scanning + push protection）→ 含凭证的私有仓库**只能靠客户端前移** |
| `git worktree` 隔离多 PR | ⚠️ **未验证** | 见 [README 验证状态一览](../README.md#验证状态一览) |

> ⚠️ **本仓库自身的状态（2026-10-02 起）**：`main` 已开启分支保护**且** `enforce_admins: true`
> ——**直推 `main` 会被拒绝**，必须走：建分支 → push → 开 PR → 等 `一致性检查` 绿 → 合并。
> 这与 §一「单人仓库直接提交 `main`」**对本仓库不再成立**；两者冲突时以更严格者为准。
> 私有仓库没有这个选项，所以本项目只有公开仓库受此约束。

**还原为「管理员可直推」**（一次性 PUT，把 `enforce_admins` 改回 `false`）：

```bash
gh api -X PUT repos/<owner>/<repo>/branches/main/protection \
  -H "Accept: application/vnd.github+json" --input - <<'JSON'
{
  "required_status_checks": {"strict": true, "contexts": ["一致性检查"]},
  "enforce_admins": false,
  "required_pull_request_reviews": null,
  "restrictions": null
}
JSON
```

### 给自己部署时

1. 把 §二 的授权表**原样**抄进全局规则或项目 `AGENTS.md` 托管块——
   这张表是本文最有价值的部分，流程可以本地化，边界不该本地化。
2. 把 §三 的命令换成你自己的远端与分支命名。
3. ⚠️ **先用一个真实的小 PR 走通一遍**，再把它当成规范写进规则。
   本项目的 PR 条款之所以标注"未验证"，正是因为**没走通就被写进规则**是上一次翻车的成因
   （见 [02-实践经验.md](02-实践经验.md) 第一节「把 staging 快照当成权威源」）。

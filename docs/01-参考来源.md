**许可证注意事项**。所有链接均在 2026-09-28 实际访问验证。

> ⚠️ **诚实声明**：本项目的主体设计（托管块、第 N 次 git 编号、三侧同步与 SHA256 校验、
> 授权边界表）是**自建**的，不属于任何单一来源的移植。下列来源提供的是**局部零件**。
> 我们检索到的所有来源中，**没有任何一个**同时具备"跨项目块同步 + 可机械校验"这套机制。

## 二、逐条说明

### 1. agents.md —— 结构性依据

- **链接**：[https://agents.md/](https://agents.md/) · 仓库 [agentsmd/agents.md](https://github.com/agentsmd/agents.md)
- **许可证**：MIT

**借鉴了什么**

| 条款 | 原文要点 | 我们的用法 |
|---|---|---|
| 分层优先级 | "离被编辑文件**最近**的 `AGENTS.md` 生效；**用户聊天中的明确指令覆盖一切**" | 直接采用为全局入口 + 项目托管块的两级结构，并在块内写入"用户明确指令为准" |
| 块的正当内容 | 明确把「commit message 或 PR 规范」列为 `AGENTS.md` 适合承载的内容 | 作为"把 Git 纪律写进 `AGENTS.md`"的规范依据 |
| 无必填字段 | 就是普通 Markdown，用任意标题 | 我们因此没有引入自定义解析器 |
| 嵌套用法 | 大型 monorepo 用嵌套 `AGENTS.md`（OpenAI 主仓库有 88 个） | 印证项目级块的必要性 |

**与我们的差异**

- agents.md 是**格式规范**，不规定任何 Git 纪律内容。我们在此之上补了完整规则集。
- 它是单文件约定；我们额外引入了**块级版本号与配对标记**，以便在单文件内部做机械替换。

**许可证注意事项**

MIT，可自由使用与再分发。本项目未复制其正文，仅采用其约定与优先级规则。

### 2. Conventional Commits —— 局部条款

- **链接**：[https://www.conventionalcommits.org/en/v1.0.0/](https://www.conventionalcommits.org/en/v1.0.0/)
- **许可证**：仓库代码 **MIT**；**规范正文 CC BY 3.0**（见站点页脚）

**借鉴了什么**

1. **提交格式**：`<type>[optional scope]: <description>`，`feat`/`fix` 为核心类型，
   破坏性变更用 `!` 或 `BREAKING CHANGE:` 页脚。
2. **规范正文里的一条 FAQ，直接为我们的原子性规则背书**：

   > 如果一个 commit 同时符合多个类型怎么办？**尽可能回去拆成多个 commit。**

   这与我们从别处借鉴的「and 检验」是同一结论，但出自**规范正文**，权威性更高。
3. **revert 的推荐写法**：`revert:` 类型 + `Refs:` 页脚列出被回退的 SHA。
   我们据此为 `git revert` 补了配套的 message 约定。

**与我们的差异**

- **我们不强制使用** Conventional Commits。理由：本机既有项目已形成自己的前缀风格
  （如 `log:` / `verify:` / `fix:`），强行统一会制造无谓改动。
  我们的取舍是：**同一项目内保持一致 > 全局统一**；新项目无既有风格时推荐采用。
- 我们**不采用**其 FAQ 中"用 `git rebase -i` 修正错误类型"的建议——那会改写历史，
  与本项目的"不改写已推送历史"直接冲突。

**许可证注意事项**

⚠️ **本条最需要当心**：

- 引用**仓库代码**适用 MIT。
- 引用**规范正文**（含上表 FAQ 原文）适用 **CC BY 3.0**，必须**署名**。
  本项目在正文中已标注出处链接；若你要在自己的项目里大段引用规范正文，
  请保留 `Conventional Commits` 名称与链接署名。

### 3. langfuse/langfuse —— Safety 清单

- **链接**：[langfuse/langfuse · `.agents/skills/git-workflow/SKILL.md`](https://github.com/langfuse/langfuse/blob/main/.agents/skills/git-workflow/SKILL.md)
- **许可证**：**混合许可**（详见下方注意事项）

**借鉴了什么**

该仓库在 `.agents/skills/` 下真实地维护了一份 Git 纪律技能——这是"**同行已经这么做**"的最有力旁证
（一个生产级开源项目，把 Git 纪律写成 Agent 技能）。其 Safety 清单：

- 暂存或提交前先看 `git status`
- **不暂存无关的工作区改动**
- **不回退无关的工作区改动** ← 这一条是我们原先**没显式写**的，已补入
- 除非明确要求，不用 `git reset --hard` / `git checkout --` 等破坏性命令
- 保持 commit 聚焦且原子
- 永不把秘密或凭据加入仓库

**与我们的差异**

| 维度 | langfuse | 本项目 |
|---|---|---|
| 范围 | 单一仓库内的 Git 工作流（含 PR、发布、评审机器人交互） | 跨项目/跨 Agent/跨平台的规则同步与回退能力 |
| 分支模型 | 强制 feature branch + PR + 评审机器人 | **不强制**（大量单人本地仓库，开分支发 PR 是纯开销） |
| 发布流程 | 详细规定 release / promotion | 不涉及 |
| 编号回退 | 无 | 有（「第 N 次 git」） |

**许可证注意事项**

⚠️ **这是本项目遇到的第一个许可证陷阱**：

- langfuse **不是**标准 SPDX 许可证。其 `LICENSE` 规定：
  - `ee/`、`web/src/ee/`、`worker/src/ee/` 目录下的内容适用 **商业许可**（见 `ee/LICENSE`）
  - **上述目录之外**的内容适用 **MIT Expat**
- 本项目只参考了 `.agents/skills/git-workflow/SKILL.md`，**位于 `ee/` 目录之外**，
  因此属于 MIT 部分，可借鉴。
- **若你要参考 langfuse 的其他部分，务必先确认文件是否落在 `ee/` 目录内。**

### 4. openai/codex —— 仅作对照，未借鉴

- **链接**：[openai/codex · AGENTS.md](https://github.com/openai/codex/blob/main/AGENTS.md)
- **许可证**：Apache-2.0

**为什么列进来**

这是一条**反向证据**，对我们判断"自己在做什么"很重要：

> OpenAI 自家旗舰 Agent 仓库的 `AGENTS.md` 里，**一条 Git 规则都没有**。

其全文是 Rust 编码约定（crate 命名、clippy lint、模块大小上限）、测试组织
（insta 快照、Bazel/Cargo 双构建）、app-server API 规范、Python 约定、平台支持。

**结论**：把 Git 纪律写进 Agent 规则文件**不是业界默认做法**，同类实践确实稀少。
规范（agents.md）**允许**这么做，只是绝大多数项目没做。
本项目的设计属于**符合标准但超出常规**，不是照抄任何现成模板。

**许可证注意事项**

Apache-2.0，允许使用与修改，但**必须保留版权声明与变更说明**，且**不得使用其商标**。
本项目未复制其任何内容，仅作事实性引用与对比。

### 5. glennguilloux/llm-knowledge-base —— 反模式清单

- **链接**：[llm-knowledge-base · anti-patterns/git-antipatterns.md](https://github.com/glennguilloux/llm-knowledge-base/blob/main/anti-patterns/git-antipatterns.md)
- **许可证**：MIT

**借鉴了什么**

| 反模式 | 我们的用法 |
|---|---|
| `git add .` 未复核就提交 | 强化为硬禁止 + 给出 `git add -p` 作为**正向替代** |
| `git push --force` 覆盖他人工作 | 细化为"确需时只用 `--force-with-lease` 且限自己分支" |
| 秘密提交后极难移除 | 补入"防线前移到根本不提交"；`.gitignore` 本身应入库 |
| 用 `git add .` 不用 `git add -p` | 采纳为"混杂改动"的推荐处理方式 |

**与我们的差异**

- 该文档面向**人类开发者**的通用 Git 教学；本项目面向**AI Agent 的规则约束**，
  因此额外强调"授权边界"（哪些动作默认授权、哪些必须停下确认）。
- 它未涉及跨 Agent 规则同步。

**许可证注意事项**

MIT，可自由使用。本项目未复制其示例代码。

### 6. yonatangross/orchestkit —— 原子提交定义

- **链接**：[orchestkit · plugins/ork/skills/commit/rules/atomic-commit.md](https://github.com/yonatangross/orchestkit/blob/main/plugins/ork/skills/commit/rules/atomic-commit.md)
- **许可证**：MIT

**借鉴了什么**

这是我们**最有价值的单条借鉴**：

> **原子性检验（五问）**：一个 commit 是原子的，当且仅当全部成立——
> 只做一件事／代码库仍可工作／message 标题不需要出现 "and"／能独立 revert 而不破坏其他功能／
> 审查者无需外部上下文即可理解。

以及配套的**「and 检验」**：

> 如果你描述这个 commit 时必须说"和"，那它就是两个 commit。

再加三条检测启发式：**目录扩散**（改动横跨互不相关目录）、**类型混合**
（同一 commit 混有 `feat` 与 `fix`/`chore`）、**文件数阈值**（暂存 > 10 个需人工复核）。

**与我们的差异**

- 我们把它**内联进托管块**，使每个项目无须外部引用即可自查。
- 我们额外补了"格式化噪声与逻辑改动分开提交"（该文档亦有类似条目，我们做了合并表述）。

**许可证注意事项**

MIT，可自由使用与再分发。本项目采用了其**判定标准**（属于方法/规则，不受版权保护），
未复制其正文段落。

## 四、借鉴与自建的边界

为免夸大借鉴程度，明确区分：

| 组成部分 | 来源 |
|---|---|
| 授权边界表（默认授权 / 需单独授权 / 禁止） | **自建**（部分思想来自使用者既有体系） |
| 「第 N 次 git」编号回退 | **自建**（使用者既有体系） |
| 托管块 + 配对标记 + 版本号 | **自建** |
| 跨项目块 SHA256 一致性校验 | **自建** |
| 三平台字节一致的平台中立块 | **自建** |
| 原子性检验五问 / and 检验 | 借鉴自 orchestkit（MIT） |
| 拆多 commit 的规范依据 | 借鉴自 Conventional Commits FAQ（正文 CC BY 3.0） |
| `git add -p` / `--force-with-lease` / 反模式 | 借鉴自 llm-knowledge-base（MIT） |
| "不回退无关改动"等 Safety 清单 | 借鉴自 langfuse（MIT 部分） |
| 分层优先级 / 块内容正当性 | 依据 agents.md 规范（MIT） |

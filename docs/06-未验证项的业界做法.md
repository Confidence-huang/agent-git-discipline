# 06 · 未验证项的业界做法（调研）

> **这份文档解决什么**：`README.md` 的「验证状态一览」里那些 ⚠️ / 🟡 / ❌ 的项，
> 在本仓库单打独斗是推不动的。本节记录**别人怎么做**（附可回溯的官方文档 URL 与**逐个核实的许可证**），
> 并给出**我们可以照做的动作**与**仍然不确定的东西**。
>
> **诚实边界**：本文的结论分三类，正文逐条标注——
> `[官方]` 官方文档/源码；`[实测]` 本机跑出来的（git 2.55.0 / opencode 1.18.25 等）；
> `[社区]` 社区经验或 issue，未获官方背书；`[未核实]` 看到了但没读到原文。
> **本仓库的规矩是宁可标 🟡，也不把"读过文档"写成"已验证"。**

## 二、四家 Agent（+ Copilot）的规则入口与技能机制

**核心结论** `[官方]`：**`.agents/skills/` 已是事实上的跨 Agent 技能别名**——
Cursor、Gemini CLI、GitHub Copilot 的官方文档都把它列为发现路径，Codex 同族也用；
**只有 Claude Code 不读它**（要 `.claude/skills/` 或 `~/.claude/skills/`，且**官方允许软链**）。
⇒ 一个 `git-discipline/` 目录 + 一条 Claude 侧链接，就覆盖这 4 家 + 已实测的 Codex / DSH。

### Claude Code `[官方]`

- 记忆文件从宽到窄**全部拼接**（不覆盖）：`/etc/claude-code/CLAUDE.md`（managed policy）→
  `~/.claude/CLAUDE.md` → 项目 `./CLAUDE.md` / `./.claude/CLAUDE.md` → `./CLAUDE.local.md`。
- **`AGENTS.md` 只在「工作目录及以上没有 `CLAUDE.md`/`CLAUDE.local.md`」时才读**
  （v2.1.277+，默认 `claude-md-or-agents-md`；可改成 `claude-md-and-agents-md`）。
  → **反过来说：一个用户级 `~/.claude/CLAUDE.md` 会让所有项目的 `AGENTS.md` 不再被读取。**
- 项目里想要托管块生效，最稳的是加 **2 行 `CLAUDE.md`**：`@AGENTS.md`（`@` 导入最多 4 跳）。
  Windows checkout 会把提交的软链退化成一行文本，所以**别用软链做这件事，用 `@` 导入**。
- 技能：`~/.claude/skills/<name>/SKILL.md`（用户级）/ `.claude/skills/…`（项目级）/ 插件。
  frontmatter **字段全部可选**；要能打包到 claude.ai/API 则只允许 6 个：
  `name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools`。
- 文档：<https://code.claude.com/docs/en/memory> · <https://code.claude.com/docs/en/skills>

### Cursor `[官方]`

- 四类规则：Project Rules（`.cursor/rules/*.mdc`，**必须是 `.mdc`**，普通 `.md` 被忽略）、
  User Rules（UI）、Team Rules（Dashboard）、**`AGENTS.md`**（根目录与任意子目录均支持，越具体越优先）。
- `.mdc` frontmatter：`alwaysApply: true` → 总是注入；`false` + `globs` → 命中文件时附加；
  `false` + `description` → 由 Agent 判断；都没有 → 只能 `@rule` 手引。
- 技能：项目 `.agents/skills`、`.cursor/skills`；用户 `~/.agents/skills`、`~/.cursor/skills`；
  **还兼容加载 `.claude/skills`、`.codex/skills`**。`name` **必填且必须等于父目录名**，`description` 必填。
- 文档：<https://cursor.com/docs/rules> · <https://cursor.com/docs/skills>
- `[社区]` `.cursorrules` 已从官方 rules 页消失（0.45 changelog 是分水岭），但**没有官方"已废弃"声明**。

### Gemini CLI `[官方]`

- 默认上下文文件名是 **`GEMINI.md`**（源码常量 `DEFAULT_CONTEXT_FILENAME = 'GEMINI.md'`）
  ⇒ **默认不读 `AGENTS.md`**；要读必须显式配 `.gemini/settings.json`：
  `{"context":{"fileName":["AGENTS.md","GEMINI.md"]}}`（接受 string 或 string[]）。
- 层级：`~/.gemini/GEMINI.md` → 工作区及父目录（上溯至 git 根/home）→ JIT；`/memory show` 可查。
- 技能：`.agents/skills/` 与 `.gemini/skills/`（同层 `.agents/` 优先）；激活时**UI 会弹确认**，
  不是"零摩擦自动生效"。
- 文档：<https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/gemini-md.md> ·
  <https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md>
- `[社区]` issue #28227（AGENTS.md 被静默忽略）仍 Open；PR #24913 状态 Closed，**是否合入未判定**。

### Aider `[官方]`

- **不特殊对待 `AGENTS.md`**：唯一途径是 `.aider.conf.yml` 里 `read: [AGENTS.md]`（或 `--read`），

## 三、`git worktree` 隔离

**结论** `[官方]`：`$GIT_COMMON_DIR` 在 linked worktree 中指回主工作树的 `$GIT_DIR`，
**common dir 是"同一个仓库"的规范不变量**；路径、remote、标记文件都可以被伪造或错配。

`[实测]`（git 2.55.0，本机 `--path-format` 复现）——**这条会让"完全一致"判据假阴性**：

```
主工作树    : git rev-parse --git-common-dir              → .git            （相对）
linked      : git rev-parse --git-common-dir              → /abs/path/.git  （绝对）
两者(绝对)  : git rev-parse --path-format=absolute --git-common-dir  → 均为绝对路径
```

- 安全写法只有两种：`--path-format=absolute --git-common-dir`，或取回后自己 `realpath`。
- `--absolute-git-dir` **只对 `--git-dir` 生效**，不会把 common dir 变绝对 `[官方]`。
- `[实测]` 同一分支二次检出被拒：`fatal: 'side' is already used by worktree at …`
  → 并行 agent **必须一个 worktree 一个分支**（或 `--detach`）。
- 三个边界（否则将来会被当 bug 重查）：**bare 仓**下 common dir == git dir；
  **submodule** 的 common dir 是 `<super>/.git/modules/<name>`，与父仓不同 →
  按此判据子模块是**独立仓库**（有意为之）；`GIT_DIR`/`GIT_COMMON_DIR` 环境变量被污染时
  `rev-parse` 会输出环境变量值 ⇒ 判定前 `unset $(git rev-parse --local-env-vars)` `[官方]`。
- `[官方]` 官方自称 experimental，且明确**不推荐** superproject + submodule 多点检出；
  `worktree.useRelativePaths` 会引入 `extensions.relativeWorktrees`，**破坏旧 git/旧工具链**，默认别开。
- `[官方]` 长任务/网络盘上的 worktree 用 `git worktree add --lock --reason "<id>"`，
  否则管理条目可能被 `prune` 清掉。

**业界工具**（许可证取自各自 LICENSE）：

| 名称 | 做法 | 许可证 |
|---|---|---|
| [workmux](https://github.com/raine/workmux) | `add <name>` = worktree + 终端窗口；`merge` 一条命令合并并清理 | MIT |
| [claude-squad](https://github.com/smtg-ai/claude-squad) | tmux 每 agent 一终端 + **每会话一个 worktree/分支** | AGPL-3.0 |
| [vibe-kanban](https://github.com/BloopAI/vibe-kanban) | 看板式调度，每任务一 worktree/分支 | Apache-2.0 |
| [wtp](https://github.com/satococoa/wtp) | 纯 worktree 管理 | MIT |
| [container-use](https://github.com/dagger/container-use) | **反例**：容器 + 分支，而非 worktree | Apache-2.0 |

## 四、钩子强制落地（pre-commit / pre-push）

**结论** `[官方]`：钩子目录默认 `$GIT_DIR/hooks`，而 `.git` 不入版本控制
⇒ **入库的只是"脚本可获得"，"已生效"永远是每台机器的本地事实**。
任何方案都必须有人在克隆后跑一次 bootstrap。四条路：
(a) 包管理器 `prepare`/`postinstall`；(b) 显式 `install`（`lefthook install` / `pre-commit install`）；
(c) `init.templateDir` 全局模板（之后 clone/init 的仓库自带）；
(d) `core.hooksPath` 指向入库目录。

**对本仓库的选型**：我们是 shell + python + markdown 的混合仓，**不引 husky/lefthook 的整套运行时**，
用 (d) 裸 `core.hooksPath .githooks` 最省：

```bash
git config core.hooksPath .githooks
ls -l .githooks/pre-push      # 必须有执行位：官方明确「没有执行位的钩子会被忽略」
```

`[实测]` 本仓库 `.githooks/pre-push` 已是 `-rwxr-xr-x`，`.gitattributes` 的 `* text=auto eol=lf`
也覆盖了它——**这两条是静默失效的高发点，值得机械检查**（见 §八 行动项）。

**三条必须写进文档的边界**：

1. `[官方]` `--no-verify` 是官方逃逸口（`pre-commit`/`pre-push`/`commit-msg`/`pre-merge-commit` 都支持）；
   ⇒ **客户端钩子只能当早筛，不能当门禁**。
2. `[官方]` `core.hooksPath` **不在** Git 的 protected configuration 名单里 → 它是**低信任输入**，
   `git -c core.hooksPath=/dev/null …` 可一次性禁用全部钩子。
3. `[社区]` **不要把绝对 `core.hooksPath` 写进 `config.worktree`**：
   `extensions.worktreeConfig` 让 worktree scope 覆盖共享 scope，链式后果是
   linked worktree 里触发的是**另一个 checkout 的脚本**（[anthropics/claude-code#88747](https://github.com/anthropics/claude-code/issues/88747)）。

**服务端能力对照**（决定"真门禁"能不能做）`[官方]`：

| 手段 | 可用条件 |
|---|---|
| Rulesets / 经典分支保护 / CODEOWNERS | **public 仓 Free 即可**；private 需 Pro/Team/Enterprise |
| Rulesets 的 commit-metadata 规则（正则约束提交信息） | **仅 Enterprise** ⇒ 免费仓无法用它强制 Conventional Commits，只能靠 CI |
| Merge queue | **仅"组织持有的 public 仓"**或 GHEC 的 private ⇒ **个人账号不可用** |
| pre-receive hook | **仅 GitHub Enterprise Server** |
| required status checks + Actions | public 仓 Free 可用 ⇒ **我们唯一现实的服务端门禁** |

## 五、单人仓库的 PR 门禁

**结论** `[官方]`：**PR 作者不能批准自己的 PR** ⇒ 单人仓库的 `required approvals` 只有两条路：
① 靠 admin 旁路豁免（**形式门禁**，保留 PR 留痕）；② 引入**第二身份**（第二账号 / App，**真门禁**）。
本仓库当前是 ①（`enforce_admins: true` + 必需检查 `一致性检查`，无 required reviews）。
把这两种模式写清楚，比假装自己有评审更有价值。

- `[官方]` 经典分支保护**不能给个人仓库配 bypass actor 名单**；rulesets 提供 bypass 配置。
- `[官方]` Environments 的 required reviewers 在 Free/Pro/Team 仅 public 可用，
  且提供"禁止自审"开关 ⇒ 官方立场是**自审应当被禁止**。
- 单人可用的"机器型第二人"：required status checks（CI 当第二人）、
  ruleset 的 "require workflows to pass"、`Require conversation resolution`（把 PR 模板清单变成必须 resolve 的评论）。
- 提交/发版工具定位：**commitlint**（只 lint，最轻，MIT）→ CI 里兜住 rulesets 做不到的提交信息约束；
  **release-please**（Apache-2.0）开 release PR，**正好补上缺失的人工确认点**；
  **semantic-release**（MIT）全自动、无人工闸门，配错就跑飞；**changesets**（MIT）只在多包 monorepo 值得。
- DCO：有外部贡献者前是空转；真要用只需 `git commit -s` + CI 校验。
- 提交签名：最省事是 `gpg.format=ssh` + `commit.gpgsign=true` 复用现有 SSH key
  （`[官方]` GitHub 侧需把同一把公钥**以 Signing Key 类型再登记一次**）；
  **vigilant mode 暂不要开**——未签名的历史与自动化提交会集体变 Unverified，噪音大于价值。

## 六、规则类仓库的异地备份

**结论**：本仓库的 ❌ 项（"仅本地仓库无异地备份"）**已经有现成系统**——
`bak-local-archives`（私有仓库 + systemd `bak-refresh.timer`，打 `git bundle` 推 GitHub，推失败下轮重试）。
`[实测]` 问题不在"没有方案"，而在**覆盖不全**：全机扫到 90 个 git 仓库，
其中 **50 个既无远端、也不在清单里**（含 `Project_43 电赛` 411 提交、`Project_17 vibecoding` 95 提交那类），
整棵 `D:\CodexProjects\` 从未纳入；`project_14 Multisim` 这类新仓库也没进。

- `[官方]` `git bundle` 明确可用于 **full backup of a repository**，可 `git clone <bundle>` 恢复；
  但它**只含 refs 可达的对象**——不含工作树、index、stash、仓库本地配置、hooks，
  **更不会包含 `~/.agents/skills` 这类软链**。⇒ 备份目录里要另存一份"清单文本"
  （`readlink -f ~/.agents/skills/*`、`git remote -v`、`git rev-parse HEAD`），恢复时当断言用。
- `[官方]` 别用 `cp -r` 直接拷仓库（可能拷到写一半的状态）。
- **无 git 跟踪的用户级文件**（`~/.codex/AGENTS.md`、`~/.gitconfig`、
  `C:\Users\Lenovo\.codex\AGENTS.md`）**不在任何 bundle 里**，必须显式白名单：
  要么进 restic/kopia 快照，要么 `rclone copy`（不是 `sync`）到云。
  **不要整目录备份 `~/.codex/`**——里面可能有 auth/会话类文件。
- **红线（凭据不入备份）**：`~/.git-credentials`、`~/.config/gh/hosts.yml`、
  `~/.config/rclone/rclone.conf`（`[官方]` rclone crypt 的密码在配置里只是 **lightly obscured**，
  只有开 configuration password 才是真保护）、`~/.ssh/id_*`、`.env`、各 Agent 的 auth 文件。
- **不要用 OneDrive/iCloud 目录当"备份"**：那是**同步**语义，删除会传播；
  macOS 的 iCloud Drive 还可能"优化储存空间"驱逐本地副本。

工具与许可证（`[官方]` LICENSE 原文核实）：restic **BSD-2-Clause**（原生支持阿里云 OSS 与 `rclone:` 后端）、
kopia **Apache-2.0**（原生 rclone 后端，含 OneDrive）、borg **BSD-3-Clause**（远端需能跑 `borg serve`）、
rclone **MIT**、age **BSD-3-Clause**。

**备份也要演练**：3-2-1 只保证副本数、不保证可恢复。每条链路配一条自检——
`git bundle verify` + `git clone <bundle>` 到临时目录、`restic check`、`rclone cryptcheck`。

## 七、macOS 平台

**结论**：不要在规则/配置里**复制**三份文件，用工具的平台变量表达差异。
`[官方]` **chezmoi**（MIT）用模板变量 `chezmoi.os`/`arch`/`hostname`/`kernel`，
有 macOS/Linux/Windows 四份官方分平台指南；**yadm**（GPL-3.0）用文件名后缀
`##os.Darwin`/`##os.Linux`/`##os.WSL`/`##default`——它**把 WSL 单独报成 `WSL` 而非 `Linux`**，
正好能区分我们的三种环境；**dotbot**（MIT）没有 OS 抽象层，只适合当一次性引导器。

路径约定（与现有 Windows/WSL 约定对应）：

| 我们的现状 | macOS 对应 |
|---|---|
| `E:\CodexBackups` | `/Volumes/<卷名>/CodexBackups` |
| `/mnt/e/CodexBackups` | 同上（macOS 没有 `/mnt/*`） |
| `C:\Users\<user>\.codex\AGENTS.md` / `~/.codex/AGENTS.md` | `/Users/<user>/.codex/AGENTS.md` |
| — | 用户级数据 `~/Library/Application Support/<App>/`；**凭据在 Keychain（不是文件）** |

`[官方]` Time Machine 的定位是**整机版本化恢复**（外置 USB / SMB NAS / AirPort 基站），
**同址性质，不能充当 3-2-1 里的那份异地**；它与 restic/rclone 是互补而非替代。
`[官方]` 读 `~/Library/Mail`、`~/Library/Safari` 等受限目录需要给终端/备份工具
**完全磁盘访问**，否则拿 `Operation not permitted`。
`[未核实]` APFS 默认大小写不敏感、Homebrew 前缀随架构（Apple Silicon `/opt/homebrew`）——
落地前用 `diskutil info / | grep -i case` 与 `command -v brew` 本机确认。

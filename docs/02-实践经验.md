# 02 · 实践经验

本文按主题归纳：**踩过的坑**（含复现步骤）、**已验证可行的做法**、**尚未解决的问题**。

所有条目均来自真实操作记录，路径已脱敏为占位符：

| 占位符 | 含义 |
|---|---|
| `$HOME` | Linux/WSL 用户家目录 |
| `%USERPROFILE%` | Windows 用户目录 |
| `<skills-root>` | 跨 Agent 共用技能实体根 |
| `<projects-root>` | 项目根目录 |
| `<backup-root>` | 备份根（各平台取值见 [04-环境支持.md](04-环境支持.md)） |

## 一、规则治理的坑

### 坑 1：把 staging 快照当成权威源

**现象**：全机搜索某条规则的关键词，只命中一个 `staging/` 目录，于是断定"规则从未生效"。
实际权威源在另一个平台的活动目录里，只是**没搜到**。

**根因**：只在一个平台（如 WSL）内搜索，而规则实际分布在两个平台。
staging 目录的时间戳比活动文件**旧 5 天**，是陈旧副本。

**复现步骤**

```bash
# 只在 Linux 侧搜索 —— 会得到错误结论
grep -rl "已git\|第 N 次 git" $HOME --include="*.md"

# 必须同时搜索挂载的 Windows 侧
grep -rl "已git\|第 N 次 git" /mnt/c/Users/*/  --include="*.md"
grep -rl "已git\|第 N 次 git" /mnt/d/          --include="*.md"
```

**修复**：判定"权威源"必须**跨平台搜索 + 比对文件时间戳**，
并优先采用**被实际加载路径引用**的那一份。

**教训**：`staging` / `backup` / `.bak` 里的内容不是事实，只是历史。

### 坑 2：规则自相矛盾导致"零回退点"

**现象**：一个项目连续数月没有任何 commit，工作区却堆满改动。

**根因**：同一套规则里存在两条冲突表述——

| 位置 | 表述 |
|---|---|
| 下发的托管块 | "日志机制**永不** commit、tag、push……" |
| 权威源 | "用户已**全局授权**本地 commit 为默认收尾动作" |

Agent 读到前者，倾向于**不提交**。

**第二层冲突**：全局规则里把 `git branch/commit/push` **并列**要求"等待用户明确确认"，
而项目托管块说"通过验证的原子改动**立即** commit"。同样导致 Agent 选择等待 → 不提交。

**复现步骤**

```bash
# 找出措辞冲突
grep -rn "永不 commit\|不允许提交" --include="*.md" .
grep -rn "已全局授权\|立即.*commit" --include="*.md" .

# 确认实际后果：查零提交仓库
for d in */; do
  [ -d "$d/.git" ] || continue
  n=$(git -C "$d" rev-list --count HEAD 2>/dev/null || echo 0)
  [ "$n" -eq 0 ] && echo "零提交仓库: $d"
done
```

**修复**：把"永不提交"限定为**日志机制本身**的作用域，
并明确"本地 commit 已默认授权"，同时把 `commit` 从需确认清单中移除。

**教训**：规则之间必须做**冲突检查**，而不只是"每条都写清楚"。

---

### 坑 3：托管块标记格式漂移

**现象**：同一份托管块在 22 个项目里长出 **5 种标记格式**，内容深度从 3 行到 17 行不等。

**实测的 5 种格式**

```
<!-- GLOBAL-PROJECT-LOG-RULES:START -->   ... <!-- ...:END -->
<!-- GLOBAL-PROJECT-LOG-RULES:BEGIN -->   ... <!-- ...:END -->
<!-- GLOBAL-PROJECT-LOG-RULES START -->   ... <!-- ... END -->
<!-- GLOBAL-PROJECT-LOG-RULES -->              （只有开头标记）
<!-- GLOBAL-PROJECT-LOG-RULES: 一句话 -->       （内联单行）
```

**根因**：模板只给了"复制这段"的说明，**没有规定块边界**。
一旦某个项目手改过，后续就无法定位块的起止，只能人眼比对 → 必然继续漂移。

**复现步骤**

```bash
# 统计各项目的标记格式差异
for f in */AGENTS.md; do
  printf "%-40s %s\n" "$f" "$(grep -o 'GLOBAL-PROJECT-LOG-RULES[^-]*-->' "$f" | head -1)"
done
```

**修复**：固定**配对标记 + 版本号** `:START v2` … `:END`，
并把"块是一整段、必须整段替换"写进模板说明。

**教训**：**没有配对边界的托管块，等于没有托管块。**

### 坑 4：项目身份硬编码 → 规则块自我否定

**现象**：某项目的 `AGENTS.md` 里，托管块开头声明：

> 本规则适用于 canonical **`Project_17 vibecoding`** checkout，
> 且仅适用于规范化后 Git common dir 与之完全一致的 worktree。

但这个文件其实位于**另一个项目**里。按它自己的字面规定，它**不适用于所在仓库**。

**根因**：托管块从别的项目整份复制，**身份文本没改**。
更糟的是这个块的"身份判定"逻辑本身写死了项目名，而不是运行时判定。

**复现步骤**

```bash
# 找出托管块里写死项目名、且与所在目录不符的情况
for f in */AGENTS.md; do
  proj=$(basename "$(dirname "$f")")
  # 块内出现的 Project_XX 字样与所在项目名不符即可疑
  grep -o 'canonical `[^`]*`' "$f" | while read -r m; do
    case "$m" in *"$proj"*) ;; *) echo "$f 身份可疑: $m";; esac
  done
done
```

**修复**：身份判定改为**运行时读 Git common dir**，块内**不写死项目名**。

**教训**：**可复制的模板里不能出现只对某个项目成立的常量。**

## 二、Git 基线的坑

### 坑 5：全局 Git 身份未设置 → 根本无法提交

**现象**：`git commit` 报错，Agent 因此无法建立任何回退点。

```
Author identity unknown
*** Please tell me who you are.
```

**根因**：`~/.gitconfig` 里只有 `init.defaultBranch`，
**没有 `user.name` 和 `user.email`**。而历史提交能成功，是因为那些提交来自另一个平台
（那边配了身份），或由 Web UI 产生——这掩盖了问题。

**复现步骤**

```bash
git config --global user.name  || echo "未设置"
git config --global user.email || echo "未设置"

# 用一个临时仓库做真实提交测试（不影响任何项目）
d=$(mktemp -d) && cd "$d" && git init -q \
  && echo x > f && git add f && git commit -q -m t && echo "可提交" || echo "不可提交"
cd - >/dev/null && rm -rf "$d"
```

**修复**

```bash
git config --global user.name  "<your-name>"
git config --global user.email "<id>+<user>@users.noreply.github.com"
```

用 GitHub 隐私邮箱可让提交正确归属账号，同时不暴露真实邮箱。

**教训**：**"能 clone 能 pull"不代表"能提交"。** 身份必须单独验证。

### 坑 6：暂存区滞留 —— 有 add 无 commit

**现象**：某项目 `git init` 后执行过 `git add`，但**从未 commit**。
47 个文件在暂存区滞留 25 天，另有 14 个新文件未跟踪——**61 份成果零还原点**。

**根因**：把 `git add` 当成了"存档"动作。`add` 只写索引，**不产生任何回退点**。

**复现步骤**

```bash
git status --short --branch | head -1   # 看到 "No commits yet on main"
git ls-files | wc -l                    # 索引里有文件
git rev-list --count HEAD 2>/dev/null   # 但 0 个提交
```

**修复**：按路径显式暂存后立即 commit（**不要**用 `git add .`）：

```bash
git add AGENTS.md PROJECT_LOG.md inputs outputs work
git diff --cached --name-only | wc -l          # 复核范围
git diff --cached --name-only | grep -Ei '\.env|token|credential|\.key$|\.pem$'   # 查敏感文件
git commit -F - <<'EOF'
chore: 建立项目 git 基线，修复零提交回退空洞

- 此前仅 add 未 commit，暂存区滞留 25 天，无任何还原点
- 已核对无凭据、无密钥、无 >5MB 大文件
EOF
```

**教训**：**回退点只由 commit 产生。** `add` 不是存档。

### 坑 7：父目录的空 git 仓库会"包住"子目录

**现象**：一个 0 提交、0 暂存的 `.git` 出现在某个**父目录**里（如项目根的上层）。
它会改变工具对"项目根"的判定，进而影响技能发现、规则加载与 `git status` 结果。

**根因**：多数 Agent/工具用"**含 `.git` 的最近祖先目录**"判定项目根。
父目录里一个空仓库，会让所有未自建仓库的子目录都被判定归属它。

**复现步骤**

```bash
# 找出 0 提交的仓库
for h in $(find . -maxdepth 4 -name HEAD -path "*/.git/HEAD"); do
  d=$(dirname "$(dirname "$h")")
  n=$(git -C "$d" rev-list --count HEAD 2>/dev/null || echo 0)
  [ "$n" -eq 0 ] && echo "空仓库: $d"
done

# 从子目录看项目根落在哪
cd some/sub/dir && git rev-parse --show-toplevel
```

**修复**：需**用户决策**——删除该空仓库，或正式初始化它。
不要擅自删除（属于破坏性操作，需单独授权）。

## 三、跨平台环境的坑

### 坑 8：DrvFs 上 `cp -p` 会失败

**现象**：从 WSL 向挂载的 Windows 盘复制文件时：

```
cp: preserving times for '...': Operation not permitted
```

**根因**：`/mnt/c`、`/mnt/d`、`/mnt/e` 是 DrvFs（Windows 文件系统），
不支持 `utimes` 等 POSIX 时间戳设置。

**复现步骤**

```bash
touch /tmp/t.txt
cp -p /tmp/t.txt /mnt/e/ 2>&1        # 报错
```

**修复**：用普通 `cp`，并在备份后**逐文件 SHA256 校验**（而不是依赖时间戳）：

```bash
cp "$src" "$dst"
[ "$(sha256sum <"$src" | cut -d' ' -f1)" = "$(sha256sum <"$dst" | cut -d' ' -f1)" ] \
  && echo OK || echo "校验失败"
```

---

### 坑 9：钩子调用 `pwsh`，但项目规则禁止 `pwsh`

**现象**：某项目的 `.codex/hooks.json` 三个钩子（SessionStart / PreCompact / Stop）
全部调用 `pwsh -NoProfile -File scripts/xxx.ps1`，
而同一项目的 `AGENTS.md` 写着"**不得把 `pwsh` 作为 Linux 日常入口**"。

**根因**：项目从另一个平台整份复制而来，钩子文件与规则文件**没有一起适配**。
连钩子里的 `statusMessage` 都还写着原项目名。

**复现步骤**

```bash
grep -n "pwsh" .codex/hooks.json
grep -n "pwsh" AGENTS.md          # 两条规则互相打架
```

**修复**：二选一——(a) 为历史脚本明确豁免，或 (b) 迁移到平台原生入口。
**不要留着一个自相矛盾的状态**。

---

### 坑 10：远端是静态 bundle，无法推送

**现象**：项目有 87 次提交，看起来有远端，但**没有任何异地备份**。

**根因**：`origin` 指向一个 `.git.bundle` **文件**，不是活的仓库。

```
origin  /mnt/d/.../project.git.bundle (fetch)
origin  /mnt/d/.../project.git.bundle (push)
```

bundle 是只读快照，**无法接收 push**。

**复现步骤**

```bash
git remote -v                       # 看远端是不是 .bundle / 本地路径
git fetch --dry-run origin 2>&1     # bundle 只读
```

**修复**：补一个真实远端（如 GitHub 私有仓库）。**bundle 只能作为归档，不能作为备份终点。**

## 四、已验证可行的做法

以下做法均已**实测通过**，附验证命令。

### A. 块一致性用 SHA256 机械校验

```bash
python3 scripts/verify_blocks.py \
  --block configs/block/GLOBAL-PROJECT-LOG-RULES.v2.md \
  --targets targets.txt
# 输出：基准哈希 + 每个文件是否一致 + 合计 n/n
```

**实测结果**：25/25 处字节一致（WSL 8 项目 + opencode 14 项目 + 模板骨架 + 两份技能模板）。

**要点**：校验必须**提取标记之间的内容**再哈希，而不是哈希整个文件
（否则文件其他部分的差异会污染结果）。

---

### B. 四条回退链路（全部实测）

| 链路 | 命令 | 实测结果 |
|---|---|---|
| 撤销某次提交（保留历史） | `git revert --no-edit HEAD` | ✅ 提交数 +1，历史未改写 |
| 按「第 N 次 git」反查 SHA | `git rev-list --first-parent --reverse HEAD \| sed -n 'Np'` | ✅ 三次均正确定位 |
| 单文件恢复到指定提交 | `git restore --source=<sha> <file>` | ✅ 不影响 HEAD |
| 误操作 `reset --hard` 后救命 | `git reflog` + `git reset --hard <sha>` | ✅ 成功找回 |

**编号计算**：`git rev-list --first-parent --count HEAD`

---

### C. 技能热加载（无需重启）

**实测**：把 `SKILL.md` 放入技能根后，**下一步**即出现在 Agent 的技能目录中，无需重启会话。

**已验证的发现路径**（以 DeepSeek Harness 为例，rank 由小到大）：

| Rank | 来源 | 路径 |
|---|---|---|
| 100 | project-dsh | `<projectRoot>/.dsh/skills` |
| 200 | project-agents | `<projectRoot>/.agents/skills` |
| 400 | user-dsh | `$DSH_HOME/skills` |
| 500 | user-agents | `~/.agents/skills` |
| 600 | bundled | 随包提供 |

**注意**：`references/`、`assets/` 等**子目录下的编辑不触发热加载**，只有技能目录本身的增删改名才触发。

---

### D. 平台中立块让"同步"可机械验证

**做法**：块内**不写死盘符与路径**，改为按平台列出取值：

```markdown
- 无 git 跟踪的用户级文件，改前备份到本平台备份根，写入前核对目标盘可用与空间，写入后逐文件校验：
  - Windows Codex：`E:\CodexBackups\<类别>\<时间戳>`
  - WSL：`/mnt/e/CodexBackups/<类别>-<时间戳>/`
  - opencode：`E:\OpenCodeBackups\<类别>\<时间戳>`（**不与 Codex 备份混放**）
```

**效果**：同一份字节可用于三个平台，同步结果**可用哈希判定**，不再靠人眼。

**若不做平台中立会怎样**：每个平台一份变体 → 变体数量随平台数增长 →
回到"人眼比对"的老路。

## 五、尚未解决的问题

诚实列出，**没有解决**的问题：

### 1. 仅本地仓库没有异地备份

多个仓库有完整本地历史但**无远端**。本地磁盘损坏即全部丢失。
`git` 保护的是"改错能回退"，**不保护"磁盘坏"**。

**待办方向**：补远端（建议私有仓库），或至少定期 bundle 归档 + 校验。

---

### 2. 无 CI 侧自动化校验

目前的块一致性校验是**手动运行脚本**。若有人在项目里手改了块，
只有下次跑校验才会发现。

**待办方向**：GitHub Actions 在 PR 上跑 `verify_blocks.py`。
参考 [langfuse 的 PR 标题校验 workflow](https://github.com/langfuse/langfuse/blob/main/.github/workflows/validate-pr-title.yml) 的做法。

---

### 3. `git worktree` 隔离未验证

多人/多 Agent 并行改同一仓库时，worktree 是理论上的正解。

**为什么没做**：调研到的 [Upsun 文章](https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents)
正文被截断，**具体条款未验证**；且本项目当前场景以单人本地仓库为主，需求不迫切。

**现状**：仅作为**需授权的手动手段**保留（见 `skills/git-discipline/references/rollback-manual.md`）。

---

### 4. pre-commit 钩子未实施

自动拦截秘密与大文件的方向是对的，但需要给每个仓库写 `.pre-commit-config.yaml`
并安装钩子（属于写操作，需逐个授权）。

**现状**：列为可选增强，未实施。

---

### 5. macOS 平台未验证

块的平台中立设计**理论上**支持 macOS，但**没有实测**。
路径习惯（备份根位置）、`cp` 行为、技能发现路径均未在 macOS 上验证。

---
